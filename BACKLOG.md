# Backlog

Requested features and known bugs. Anything that changes the tech stack, grading rules, or engine API needs a proposal and a [SPEC.md](SPEC.md) update first.

- ~~Countdown before each attempt~~ and ~~basic sound feedback for app events~~ (requested 2026-10-30, Layer 4 review): done in Layer 5 Part A, see [DECISIONS.md](DECISIONS.md).
- **Hear the on-time window in Hear timing** (possible feature, requested and then shelved 2026-10-30). Let the timing preview also convey each step's wiggle room, not just its target moment.
  - Tried: an optional sustained tone spanning each step's on-time window (from the start of frame `target − tolEarly` to the end of frame `target + tolLate`), playing under the press tone, with a dashed outline on the step card during the window. Steps with no tolerance got no window tone. The user wasn't happy with how it turned out and it was removed before committing.
  - Sound settings tried: a 370 Hz triangle at level 0.3 (too loud, too deep), then a 622 Hz sine at 0.12, a minor third below the 740 Hz press tone. The idea may need a different approach rather than a different tone, e.g. two short ticks marking the window's edges, or a visual-only window.
- **Advanced combo-building mode** (requested 2026-10-30, after the Layer 3 review). An optional editor mode for steps that need more than one button press:
  - **Release events as steps:** grade the timing of a button release, not only presses (e.g. negative-edge inputs, or holding a button for a set number of frames). The input layer already emits releases (see [DECISIONS.md](DECISIONS.md), "Release events").
  - **Grouped inputs:** a step made of several inputs. They can be *sequential*, like a motion input (quarter-circle forward = DOWN, DOWN+RIGHT, RIGHT, then a button), or *simultaneous*, like a chord (two buttons within a few frames of each other). ~~Button chords~~: done 2026-11-01, see [DECISIONS.md](DECISIONS.md), "Chords". Motions are still open.
  - **Input leniency for motions:** accept shortcuts the way many games do, e.g. DOWN → RIGHT counts as a quarter-circle forward even though DOWN+RIGHT was skipped. Leniency should be adjustable per group.
  - Motion inputs are out of scope for now (SPEC §9). This changes the engine's `Step` type and grading, so a written proposal and spec update come before any code ([CLAUDE.md](CLAUDE.md)).
- **Negative edge input support** (requested 2026-10-31). Let a step be graded on a button's release instead of its press, so drills can practice negative-edge inputs (holding a button, then letting go on the right frame). The input layer already emits releases (see [DECISIONS.md](DECISIONS.md), "Release events"), but the engine and editor only handle presses. Overlaps with "Release events as steps" above. This changes the `Step` type and grading, so a proposal and spec update come first ([CLAUDE.md](CLAUDE.md)).
- **Charge input support** (requested 2026-10-31). Let a step require holding a direction (e.g. back or down) for at least a set number of frames, then pressing the opposite direction and/or a button within a short window (e.g. charge back, then forward + punch). Needs: a minimum charge time per step, a rule for how long the charge stays valid after release, and feedback on how many frames were charged. Builds on release events and the grouped inputs above, and is listed as out of scope in SPEC §9 for now. This changes the `Step` type and grading, so a proposal and spec update come first ([CLAUDE.md](CLAUDE.md)).
- **Mashing shouldn't cause failures** (requested 2026-11-01). Players often mash a button to make sure a link comes out (e.g. pressing it several times around the target frame). Today an extra press grades early (the first press of the right button is graded) or, in strict mode, a press of another button ends the attempt with `WRONG_BUTTON`. Let mashing not count as a failure. Open questions for the proposal:
  - Which press counts when the right button is pressed several times near a step: the first one inside the on-time window, the closest to the target, or the first one at all (today's rule)?
  - Should extra presses of the button just graded (or the button awaited) be ignored instead of graded as early or wrong?
  - Should it be a setting (e.g. a "mash-friendly" toggle, off by default) or the new default, and how does it interact with strict mode?
  - How to show ignored mash presses in the timeline and feedback (non-strict mode already gives ignored presses their own lane).
  - This changes grading (SPEC §3), so a proposal and spec update come first ([CLAUDE.md](CLAUDE.md)).
- **Bug: metronome tick on target frames doesn't always work as intended** (reported 2026-10-30). Symptom: ticks were missing entirely in the attempts the user watched on another computer (not the dev machine). Timing mode and combos not yet recorded. Get a repro before fixing. Things to check:
  - Settings are saved per browser (`localStorage`) and the metronome is off by default, so on a new computer it may simply have been off. Rule this out first.
  - Audio may not have started on that computer: browsers block sound until the page gets a user gesture, and a gamepad press may not count as one. Check whether other sounds (countdown, on-time/miss) played there.
  - Relative mode only knows the awaited step's tick after the previous press, and ticks already in the past are skipped by design (see [DECISIONS.md](DECISIONS.md), "Metronome"). Short gaps may make ticks look like they are missing.
  - Relative ticks are timed from the previous press's exact timestamp, so they will move once the approved fixed frame grid lands. Fix and test both together.
  - Ticks are cancelled when their step is graded or the attempt ends; check that a still-needed tick isn't cancelled early, and that a stale one isn't left playing.
- **Bug: same-frame presses on a plain button step grade differently depending on pad button order** (found 2026-11-02, direction+button interview). The engine grades one press at a time, and a gamepad poll sends its events in a fixed order: buttons by index, then stick axes, then hat directions ([src/input/gamepad.ts](src/input/gamepad.ts), `poll`). So when the awaited button and a wrong one land in the same poll, the result depends on which comes first in that list:
  - Step MK, stray LP in the same poll: MK (index 1) comes first and is graded; LP goes to the next step.
  - Step LP, stray MK in the same poll: MK comes first and the attempt ends `WRONG_BUTTON` (strict).
  - A game would read both on the same frame either way. Keyboard presses have separate timestamps, so it mostly affects pads. Chords already avoid this (a complete chord stays open to the end of its frame). The planned fix is the frame snapshot proposal (SPEC §9, "Frame snapshots"; [NEXT_SESSION.md](NEXT_SESSION.md)) rather than another one-off rule.
